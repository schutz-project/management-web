# 모니터링 고도화 1단계: 시간 범위와 서버 자원 추이

## 범위

- 지표 조회 범위: 최근 15분 / 1시간 / 6시간 / 24시간
- 앱·DB 및 경로별 앱/프록시 지표에 동일 범위 적용
- 서버별 CPU·메모리·루트 디스크 사용률 추이, 현재 값, 표시 표본 평균·최대·표본 수
- 조회 기간 URL 저장 및 새로고침 복원
- 4개 범위별 캐시 분리, 응답당 시계열 최대 300점
- 현재 경보·수집 대상 및 최근 5분 로그는 지표 조회 범위와 구분
- DB 구조·데이터·Worker·FastAPI·서버 배포 설정 변경 없음

## 수치 해석과 제한

평균은 조회 간격으로 평가된 유효 표본의 산술평균입니다. 누락값은 제외하며 실제 원시 데이터 전체의 시간 가중 평균이 아닙니다. p95 그래프의 평균·최대도 구간별 p95 표본에 대한 값으로, 선택 기간 전체 요청의 p95가 아닙니다.

15분·1시간은 30초, 6시간은 120초, 24시간은 300초 간격입니다. 긴 기간은 더 성긴 추세이므로 그 사이의 짧은 피크를 모두 보장하지 않습니다. CPU는 기존 5분 rate 기준, 디스크는 루트 파일시스템만 표시합니다.

수집이 지연돼도 조회 가능한 과거 그래프는 유지하지만 현재 값은 정상으로 표시하지 않습니다. 조회 실패·수집 지연·데이터 없음은 구분합니다. Loki의 긴 기간 조회가 제한 시간 안에 완료되지 않으면 해당 패널만 조회 실패로 표시합니다. 실제 서버에서 24시간 조회 성능과 각 범위 수치 비교는 배포 후 검증 대상입니다.

위 브랜치는 코드 기준점이며 AWS 전체·DB 전체의 시점 스냅샷은 아닙니다. 배포 전 실행 중 이미지가 기준 태그와 동일한지, 이전 이미지가 보존돼 있는지 확인합니다. 서버 엔지니어의 별도 설정 변경이 있으면 복구 범위를 다시 기록합니다. 기존 자동 배포는 이미지 교체 전 Compose와 이전 이미지 참조를 서버의 .release-backups에 보관합니다.

## 피드백 후 원상복구

방향이 맞지 않으면 새 기능을 추가 수정하는 대신 위 기준 이미지로 복구할 수 있습니다. 이번 단계는 DB 변경이 없으므로 이 단계에서 생성한 별도 데이터 마이그레이션은 없습니다. 기존 사건·조치 기록은 계속 보존합니다.

기존 Management Manual Release 워크플로를 사용하되 오래된 기본 이미지 태그를 사용하지 않습니다.

1. 현재 Worker 이미지가 위 기준과 동일한지 확인합니다. 다르면 함께 되돌릴지 범위를 먼저 결정합니다.
2. 위 Web·Worker 태그를 명시해 CHECK를 실행하고 정상 사전 검사 결과를 확인합니다.
3. DEPLOY, rollback_test=NO, confirmation=DEPLOY로 실행합니다. 이 경로는 두 컨테이너를 재생성하므로 Worker가 기준과 같을 때 사용합니다.
4. 복구 후 기준 이미지 확인, Web 건강 검사, Worker 수집, DB 상태, 기존 화면·로그인·사건 이력을 확인합니다.
5. 코드도 기준 상태를 유지해야 하면 이 기능 PR을 되돌리는 PR을 별도로 만들고, main 자동 배포 영향을 검토합니다.

자동 건강 검사 성공 이후의 사용성 피드백은 자동으로 감지되지 않습니다. 선택한 버전으로의 수동 복구는 별도 작업입니다. 이번 PR을 실제 운영에 배포하거나 피드백 복구를 실행한 결과는 아직 없습니다.
